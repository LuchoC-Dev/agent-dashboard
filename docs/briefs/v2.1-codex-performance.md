# Brief — v2.1 first-load performance (Codex)

Branch `feat/backend`. Read `AGENTS.md` and `docs/design/v2-codex.md` (§2.5 caching, risk R2).
The user reports the first load with Codex data is very slow; after it's in memory it works fine.
Real corpus: ~240–260 Codex sessions, ~860 files, ~1.7 GB; smoke measured ~5–6 s first scan and ~160 MiB cache
in tests — measure what the **app** actually does on startup (all commands the UI calls on the first screen).

1. Profile first load end to end (`npm run tauri dev`, release build too): discovery, parsing, aggregation,
   IPC payload sizes per command, and how many commands the UI fires at startup. Write numbers in your report.
2. Optimize, keeping results identical:
   - parse in parallel with bounded memory; avoid re-reading/duplicating forked history and guardian files;
   - keep summaries/aggregates resident and load full session details lazily (only on `get_session`);
   - avoid large IPC payloads (e.g. metrics must not ship per-message data);
   - if useful, make the scan non-blocking so the UI can show Claude data while Codex is still being scanned
     (additive contract only, documented; coordinate via the final report — the frontend agent works in parallel).
3. READ-ONLY: no on-disk cache or any write; only reading session logs. Never open credentials/config.

## Done when
Before/after timings and memory in the report (target: first screen in ~1–2 s on this corpus);
`npm run check`, build and both real-data smokes pass with identical totals; conventional commits on
`feat/backend`. Don't merge, don't push.
