# v2.3 frontend verification

Brief: `docs/briefs/v2.3-frontend.md`. Branch `feat/frontend`, built against
`docs/briefs/contract-v2.3.md` with the mock. **`feat/backend` had no v2.3 implementation yet**
(only its brief), so it is not merged: the v2.3 types live in `src/lib/series.ts` and the mock
(`src/api.ts`) computes the series and the weekday/hour filter. When the backend lands: merge it,
keep its `api.ts`/mock (contract owner), import `DailySeries`/`DayPoint` and the `Metrics`/
`SessionFilter` fields from `src/bindings/` instead of `lib/series.ts`, and run
`src/api-series.test.ts` against it. Not run in the native app (`npm run tauri dev`) this round.
Screenshots are local in `.qa/v2.3/` (ignored).

## What changed

1. **Daily chart performance.** The chart reads the precomputed `series_by_*` (no trend computed
   from session summaries); it is a lazy chunk, so KPIs, tables and heatmap paint without waiting
   for Recharts; hover is outside React state (a `<style>` rule and the tooltip subscribe to a
   small store), so a hover re-renders nothing else; bars are memoized per computed trend and drawn
   with a `shape` (no `Cell` per day and series); metric/grouping switches go through
   `useDeferredValue` (buttons answer at once, the chart dims slightly and follows); panels are
   `memo` with stable callbacks; Intl formatters are built once (creating one per call was the top
   self-time function: the X axis formats hundreds of dates per render).
2. **Model filter bug.** Series are attributed per message: with `modelo=gpt-5.6-sol` every
   grouping shows only Sol 5.6's numbers (test: a session alternating Sol and Terra).
3. **Por proyecto.** Chart grouping and panel list show every project with ≥ 3 % of the selected
   metric in the current view (`PROJECT_SHARE_MIN`), the rest in "Resto · N proyectos" (chart
   segment/legend: plain, not a filter; panel: a line that opens Proyectos). A single leftover is
   never folded; a zero total folds nothing.
4. **Everything selectable filters** (audit below). New: heatmap cell → weekday+hour, weekday label
   → weekday, hour label → hour (`diasem`, `hora`; contract v2.3), tool row → `herramienta`.
   Under a weekday/hour filter the heatmap keeps the whole week (metrics without the slot,
   usually cached) with the cells outside the selection dimmed, so another slot can be picked.
5. **Por modelo bar.** Each segment: tooltip (model, cost, share, what a click does), highlight
   (grows, others dim), 150 ms transition (none with reduced motion), click → model filter.
   The KPI token bar got the same hover.
6. **Back navigation.** Back/Forward in the top bar (disabled at either end), Alt+←/→, mouse side
   buttons (native gesture cancelled, so it never leaves the app). Range, provider and filter
   changes now push history entries (search typing still replaces), so Back restores them.

## Timings

Production build with the React Profiler enabled (`react-dom/profiling`), mock mode, Chrome,
1440×900, 90-day range, real-size corpus: the sample scaled to **960 sessions / 45 projects**
(the real machine has ~940: 44 Claude + ~894 Codex). Medians; two alternating before/after runs
per row (ranges shown). "Responds": click → next paint (Event Timing). "Final": until the DOM
stops changing. "Commit": React Profiler `actualDuration` summed. Hover: 30 segments in Por
proyecto, time to the next frame.

| No throttling | Before | After |
| --- | --- | --- |
| First paint of Resumen (first bar) | 493–503 ms (React 168–171 ms) | 550–559 ms (React 73–75 ms) |
| Switch metric: responds / final | 80–96 / 106–113 ms | 32 / 105 ms |
| Grouping Por proyecto: responds / final | 64 / 87–90 ms | 32 / 95–102 ms |
| Grouping Por modelo: responds / final | 80 / 101–106 ms | 32 / 107–109 ms |
| Hover a segment: next frame (React per hover) | 95–96 ms (44 ms) | 47 ms (1 ms) |

| 4× CPU throttle | Before | After |
| --- | --- | --- |
| Switch metric: responds / final | 472–520 / 526–554 ms | 80–128 / 499–523 ms |
| Grouping Por proyecto: responds / final | 360–408 / 397–454 ms | 40–72 / 403–480 ms |
| Grouping Por modelo: responds / final | 464–496 / 486–524 ms | 40–64 / 492–537 ms |
| Hover a segment: next frame (React per hover) | 476–541 ms (303–366 ms) | 94–119 ms (6–12 ms) |

Reading: hover, the main complaint, is 4–5× faster and no longer re-renders the chart; clicks
answer 4–8× sooner. The time until a switched chart is final is unchanged (±10 %): a CPU profile
shows it is Recharts' own work per rectangle plus SVG layout/paint, not app code. First paint:
React work halves, but the mock now computes the series in JS (~45–50 ms on this corpus,
measured in Node), which the native backend does in Rust within its 50 ms budget; in the app
that cost moves off the UI thread.

## Known limits

- ~~Grouped token series count every kind.~~ Resolved since v2.4: the backend scopes every grouped
  series by the token kind, so Por proveedor/modelo/proyecto count only that kind (checked again
  in v2.6, `token-kind.test.tsx`).
- ~~Total + Herramientas no longer splits ok/error per day.~~ Resolved in v2.6: `tool_errors` per
  day brings the split back, and the groupings give each series' errors in the tooltip.
- ~~The tool filter scopes only the tool tile and table.~~ Resolved in v2.6: the metric commands
  and `list_sessions` take the tool, so every panel shows only the sessions that called it.
