# Frontend architecture

React 19 · React Router 8 (data mode) · TanStack Query 5 · Tailwind CSS 4 · Vite 8, inside a Tauri v2
WebView. The UI is read-only: it only reads through `src/api.ts` (see `AGENTS.md`).

## Structure

```
src/
  main.tsx                 createRoot + global CSS/fonts
  App.tsx                  providers (QueryClientProvider) + <RouterProvider>; nothing else
  api.ts                   the only backend entry point (Tauri invoke or mock fixtures)
  app/
    router.ts              the app's QueryClient and createHashRouter(routes), created once
    routes.tsx             the route tree: layouts, lazy route modules, loaders, handles
    loaders.ts             non-blocking prefetch loaders (+ the legacy ?vista= redirect)
    queries.ts             QueryClient defaults and the scan-report query
    shell/                 layout route: Sidebar, Topbar, DateRangeControl, notices, theme
    DataGate.tsx           pathless layout route for the list/dashboard screens (loading/error/empty)
    RouteError.tsx         route-level error boundary
  routes/                  one module per route/view; each exports `Component` and is loaded lazily
  features/
    overview/              the dashboard (KPIs, trend, heatmap, models, projects) and its data
                           hook, shared by Resumen and the project page
    sessions/              Sesiones list + session detail (summary/conversation tabs, timeline)
    projects/              Proyectos list + project header (its dashboard is overview's)
    tools/                 Herramientas ranking and matrix
      <feature>/components/  single-purpose components
      <feature>/queries.ts   queryOptions factories (keys + fetchers)
  components/ui/           shared presentational primitives (Panel, DataTable, Segments, states…)
  components/RangeLink.tsx a link that carries the current date range
  hooks/                   URL-backed hooks: date range (+ range navigation), mock fixture
  lib/                     pure logic: format, dates, models/colors, aggregations (unit-tested)
  styles/                  Tailwind entry: theme tokens, base layer, the few component classes
  bindings/                generated by ts-rs — never edited by hand
```

Rule of thumb: `lib/` has no React; `components/ui/` has no data fetching; a feature may use `lib/`,
`components/ui/`, `hooks/` and its own `queries.ts`; `routes/` compose features; only `app/` knows the
whole route tree. A few domain widgets are shared across features on purpose (the session table in
the dashboards; the KPI strip and touched-files table in the session detail). Files stay below
~250 lines (`styles/theme.css`, the token list, is the exception).

## Routing

- **Data router, hash history.** `createHashRouter` + `<RouterProvider>` (data mode). React Router
  recommends data mode for SPAs that want loaders without the framework/Vite plugin, and the hash
  router for hosts that cannot rewrite every path to `index.html` — the Tauri custom protocol and the
  `?estado=` mock fixtures both rely on the `#/…` URL.
- **Route tree.** `/` (shell layout) → pathless `DataGate` layout → `resumen` (and index),
  `sesiones`, `proyectos`, `proyecto/:key`, `herramientas`, `*` not-found. The session detail is
  outside the gate because it loads its own data: `sesion/:id` with nested tab routes — index
  (Resumen) and `conversacion`. The legacy `?vista=conversacion` URL redirects to the nested route.
- **Lazy route modules.** Each route uses the `lazy` object form to load only `Component`; loaders
  and `ErrorBoundary` stay static in the route tree so data prefetching starts in parallel with the
  chunk download (no waterfall) and a failed chunk is still caught.
- **Loaders prefetch, components read.** Loaders call `queryClient.query(options)` without awaiting
  (`.catch(noop)`), the non-blocking variant of the TanStack Query router-integration guide.
  Blocking loaders would hide the shell during the first scan; the approved UI shows the shell plus
  a scanning state, so components keep `useQuery` and render the same loading/error/empty states.
  In mock mode the API reads `?estado=` from the hash at call time, so loaders skip prefetching when
  the target URL's fixture differs from the current one (the URL commits after loaders run).
- **Outlet context, not globals.** The shell hands shared data (session list, metrics, palette,
  refresh) to its children with `useOutletContext`; `DataGate` and the session layout do the same
  for their screens and tabs. The breadcrumb title comes from each route's `handle`.
- **Error boundaries.** Every route has `ErrorBoundary: RouteError`, which renders the existing
  error state; expected data errors (I/O, not found) keep their in-page states and retry actions.

## Data

- `src/api.ts` is unchanged as the single backend entry point.
- Each feature exposes `queryOptions` factories in `features/<x>/queries.ts`
  (`sessionQueries.list(range)`, `sessionQueries.detail(id)`, `overviewQueries.metrics(range)`, …).
  Keys are hierarchical (`["sessions", "list", …]`) and include the mock fixture (`?estado=`) so the
  fixtures never share cache entries with real data.
- **The URL is the source of truth** for every filter: `from`/`to` (date range), `q`, `proyecto`,
  `modelo`, `tool`, and focus targets (`msg`, `call`, `sub`). `useDateRange()` reads and writes them;
  drilldown links keep the current range (`RangeLink`, `useRangeNavigate`). No global ad-hoc state.
  Only view state that never was in the URL (theme, selected metric, sort, page) stays local.
- `QueryClient`: `staleTime` 60 s, no refetch on focus, no retries (local files); **Refrescar**
  rescans and invalidates every query.
- **First scan.** The full session list is keyed by the providers whose scan finished
  (`scanSignature`, from `SourceScan.scanning`, contract v2.2), so a provider that finishes
  refetches it instead of trusting a partial list. `ready` (shell) says the selected provider scope
  is final; until then the shell, provider control and layout are already on screen and Resumen
  shows a skeleton per section (`handle.sections`), sized like the final section per breakpoint.
  Metrics and tool stats are never fetched or prefetched mid-scan, so a partial result is never
  cached under a final key.
- **Instant switches.** Range and provider session lists are derived client-side from the full
  list (no query); metrics, tool stats and a slot filter's sessions use
  `placeholderData: keepPreviousData` (a slow update dims the page after 300 ms, a cached one
  never flickers); once the first screen is on,
  `usePrefetchOverview` warms every provider button × range preset while the page is idle.
- **Cross-filters (Resumen).** `proveedor`, `proyecto`, `modelo`, `dia`, `diasem`, `hora`,
  `tokens`, `herramienta` in the URL (`lib/filters.ts`, `useOverviewFilters`). Every clickable
  element of Resumen applies one (segments, legend entries, project/model/tool rows, KPI
  provider lines, token kinds, Por modelo bar segments, heatmap cells and weekday/hour labels);
  a chip bar removes them and clicking the active one clears it. Provider, project, model, day,
  weekday/hour and tool go to the metric commands (contracts v2.2, v2.3, v2.6; weekday/hour
  select messages); the session lists are narrowed client-side (the slot and the tool through
  `list_sessions`); the token kind only changes what token figures count. Changing the date
  range drops `dia`. A folded "Resto" is never a filter.
- **Tool filter (v2.6).** `herramienta=Bash` (a Herramientas row, chip "Herramienta: Bash")
  goes to every query, side queries and prefetch keys included: every panel shows only the
  sessions that called the tool (KPIs, daily chart, Por proyecto/modelo/proveedor, heatmap,
  session list, Archivos más tocados, the project's branches), and the tool figures (tile,
  Herramientas in the chart, the table's single row) count only that tool's calls and errors.
  Session lists (v2.6.1) show and sort by each session's `filteredToolCalls`/`filteredToolErrors`
  from the tool's `list_sessions` (which also gets the model or family), merged by
  `withToolCounts` and read through `toolCounts` (`lib/sessions.ts`); the column is named after
  the tool. "Ver todas" carries `herramienta` into Sesiones, which narrows through the same list
  and shows a removable "Herramienta: Bash ✕". The session detail keeps all-tools counts.
- **One dashboard, many scopes.** Resumen and the project page render the same `Dashboard`
  with props from the same hook, `useDashboardData(scope)` (`features/overview`). The scope
  (`{ projectKey }`) is a fixed part of every query, never a URL filter or a chip; the rest
  of the cross-filters, the chips, clicks, skeletons, stale dimming and tooltips are the
  same code. What only a project has is keyed off `projectKey` inside the shared components:
  "Por rama" instead of "Por proyecto" in the chart (branch series from its loaded details),
  "Archivos más tocados" instead of the projects panel, and a longer session table. A fix to a
  dashboard panel or filter therefore lands once; a new scope (e.g. a model page) should be a
  new `DashboardScope` field handled in the hook, not a copy of the dashboard. The session
  detail reuses the dashboard's leaf components (`KpiStrip`, `FilesTouched`) where they apply.
- **Projects by git key (v2.5).** Everything groups, links, colors and filters by
  `projectKey` (`git:<identity>` or `path:<cwd>`) and labels with `projectName`
  (`lib/projects.ts`, `palette().projectName`). `?proyecto=` holds the key; a pre-v2.5 path
  in `/proyecto/:key` or `?proyecto=` is mapped to its key (the route redirects). The project
  header lists its working copies (distinct `projectPath`s: clones, worktrees).
- **Model families (v2.5).** `modelo=familia:opus` (family row in Por modelo, the family entry
  of the chart's model legend, the Sesiones select) goes to the commands as `models` (every
  version of the family, `modelArgs`); a single version keeps `model`. Chip: "Familia: Opus".
- **Archivos más tocados (v2.5)** is computed from the loaded details under every filter: the
  sessions on screen (provider, model, slot), then only the calls of messages of that
  model/family, weekday/hour and day (`filesTouched(details, filter)`). Token kind does not
  apply (file counts have no tokens).
- **Several homes per provider (v2.5).** Codex may report more than one `SourceScan`: the
  sidebar and the empty state list every directory (one line each), notices name the home,
  a provider is "scanned" only when all its homes are, and the session detail shows
  `sourceDir`.
- **History.** Range, provider and filter changes push history entries (typing in a search
  box replaces). The top bar's Back/Forward, Alt+←/→ and the mouse side buttons step through
  the app's own entries (`lib/history.ts`, `useHistoryNav`), so going back restores filters.
- **Daily chart (v2.3, v2.4).** Reads the backend's `series_by_provider|model|project`
  (per-message attribution); a project adds per-branch series computed from its loaded
  details (`lib/series.ts`). Under a token kind every grouping counts only that kind.
  Herramientas splits each day into calls without and with error in Total, and gives each
  series' errors in the tooltip of the groupings (`tool_errors`, contract v2.6). Por proyecto draws **every** project as its own segment; only
  the legend is limited to two lines (largest first) with "+N más" for the rest. Models and
  branches past the top 8 fold into "Resto" in the chart.
- **"Todo" span (v2.4.1).** An open range starts the daily chart at the first day with data
  in the current scope and filters (`trendSpan`, from the range-wide series) and ends it at the
  last one;
  the KPI per-day averages divide by the same days. Explicit ranges keep their full span.
- **Por proyecto panel (v2.4.1).** No "Resto": it lists the largest projects of the selected
  metric, as many as fit in the height of "Por modelo" beside it (measured with a
  ResizeObserver, so it follows expanded model rows and resizes), and "Ver todos (N) →" opens
  Proyectos.
  Performance: Recharts lays out **one bar per day** (the stacked total) and `DayStack` draws
  that day's segments as plain SVG inside its `shape`, so the cost barely grows with the
  number of series (jsdom, 30 days: 60 projects 720 → 103 ms); hover lives outside React
  state (one CSS rule + the tooltip subscribe to a small store); the Recharts tree is
  memoized per computed trend; metric/grouping switches render through `useDeferredValue`.

## Styles

- `styles/theme.css` holds the approved tokens from `docs/mockups/tokens.css` in `@theme static`,
  overridden for dark mode (OS preference unless `data-theme="light"`, or forced `data-theme="dark"`)
  and per provider (`data-provider`). Tokens become utilities: `bg-surface`, `text-ink-3`,
  `border-line`, `text-xs` (11.5 px), `rounded-md`, `shadow-pop`, `p-4` (4 px grid)…
- **App accent (v2.5.1).** The app's own color is one swappable token set, `--app-accent`
  (+ `-alt-1…3`, `-ink`, `-on`, `-wash`), never a hard-coded hex. It feeds "Todos"
  (`:root[data-provider="all"]` maps every `--brand-*` to it: KPI bar, single-measure charts,
  token kinds) and the interface emphasis (`--color-accent` = `-ink` for links, focus rings and
  selected text; `--color-accent-wash` = `-wash` for selected controls). Provider colors stay
  provider-driven. The preset is picked beside the theme switch (`AccentPicker` in the
  sidebar, `useAccent`), kept exactly like the theme (shell view state, `<html data-accent>`,
  not written anywhere), default **Bronce** (the most neutral non-green preset).
  - *Change a preset:* edit its `[data-accent="<id>"]` block in `styles/theme.css` (light values,
    then `@variant dark`). The default's block also carries `:root:not([data-accent])`.
  - *Add a preset:* add `[id, label]` to `ACCENTS` in `lib/accents.ts` and a block with all seven
    tokens in both themes. To change the default, move `:root:not([data-accent])` to its block
    and update `DEFAULT_ACCENT`.
  - *Validate:* `npx vitest run src/styles/palettes.test.ts` checks every preset in both themes:
    base + alts as an adjacent categorical set (Todos' token-kind stack), base ΔE ≥ 15 from the
    Claude and Codex bases and the ok/error marks and not green, `-ink` ≥ 4.5:1 on page, surface,
    sunken and its wash, `-on` ≥ 4.5:1 on the base; and that CSS and `ACCENTS` list the same ids.
    The free hues are few (warm reds are Claude's, blues Codex's, green is "ok", red is
    "error"): magenta–violet, teal (≥ 0.60 lightness in dark, sRGB-limited) and bronze/olive.
- `@custom-variant dark` follows the same rule as the tokens, so `dark:` utilities match the theme
  switch. Named breakpoints are custom variants with the exact original `max-width` semantics:
  `narrow` (≤1240 px), `collapsed` (≤1100 px, icon sidebar), `compact` (≤900 px), `phone` (≤640 px).
- `text-size-*` is a small `@utility` that sets only the font size from the type scale: Tailwind's
  `text-*` also sets the scale's line height, while most of the approved components inherit the
  20 px body leading.
- Dashboard tables respond to their own panel width: `table-md` / `table-sm` are custom variants
  for `@container dashboard-table (max-width: …)`.
- Components use Tailwind utilities; shared class sets (button, panel, field, note…) live in
  `components/ui/styles.ts` because a "button" can be a `<button>` or a `<Link>`. The few rules that
  depend on document structure, pseudo-elements or the page container query stay as classes in
  `@layer components` (`styles/components.css`): the data tables, the KPI strip, the loading
  skeleton and `.mono` (whose size must yield to table headers).

## Testing

- **Vitest + Testing Library** (`npm test`): unit tests for `lib/` (formatting, local days across
  time zones, aggregations against the mock fixture, hour heatmap), the mock API, and route-level
  smoke tests that render the real route tree with a memory router and mock data.
- `npm run check` (read-only guard, `tsc`, `cargo test`) and `npm run build` must pass.
- Visual parity is checked with before/after screenshots of every screen and fixture state in both
  themes (local, not committed).
